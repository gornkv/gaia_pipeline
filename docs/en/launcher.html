Short version

GAIA Experiment Launcher starts the full experimental loop:

base model backend -> Test-Time Scaling Proxy -> InspectAI / GAIA

It allows the same benchmark to run reproducibly on different inference backends and compute environments: CPU, CUDA, Google Colab, Mac / Apple Silicon, and local GPU machines.

Problem solved by the launcher

Local LLM experiments depend heavily on the runtime environment. One model may run through llama.cpp on CPU, another through llama.cpp CUDA in Colab, another through MLX on Apple Silicon, and another through vLLM on a GPU server. The benchmark runner and proxy still need the same OpenAI-compatible endpoint.

Without a launcher, every run becomes manual: start the backend, wait for the model, start the proxy, start GAIA, pass endpoint settings, save logs, clean processes, and repeat on another machine.

Launch pipeline

1. Base model backend
2. Test-Time Scaling Proxy
3. InspectAI / GAIA benchmark runner

The backend serves an OpenAI-compatible API. The proxy connects to the backend and exposes another OpenAI-compatible API to the benchmark. InspectAI / GAIA calls the proxy as the model.

Why a separate launcher

The project needs to repeatedly run different models, backends, techniques, feature flags, GAIA levels, splits, environments, and Docker/no-Docker modes. The launcher turns this into a reproducible configuration-driven process.

Supported inference modes

llama.cpp       — CPU inference
llama.cpp CUDA  — Google Colab
vLLM            — local GPU machine
MLX             — Mac / Apple Silicon

llama.cpp CPU is useful as baseline and fallback. llama.cpp CUDA supports Colab runs. vLLM targets local GPU serving. MLX supports local development and experiments on Apple hardware.

What the launcher does

The launcher starts pipeline components in order, checks endpoint readiness, cleans stale processes, stores stdout/stderr logs in one place, can save Colab state to Google Drive, uses .env for configuration, switches backend without rewriting scripts, and separates benchmark settings from backend-specific settings.

Endpoint readiness checks

Pipeline components depend on each other. InspectAI / GAIA should not start before the proxy is available. The proxy should not start work without a base model backend. The backend must first load the model and expose an endpoint.

1. Start base model backend
2. Start Test-Time Scaling Proxy
3. Start InspectAI / GAIA benchmark

A launched process is not necessarily ready to receive requests. The launcher performs readiness checks before moving to the next stage, which reduces manual errors and is especially important for heavy models and unstable environments such as Colab.

Pipeline logs

Logs are essential for debugging benchmark runs. A failure can come from model loading, proxy/backend connection, benchmark errors, missing endpoints, memory limits, configuration problems, or invalid technique responses. The launcher stores stdout/stderr logs for all parts in one place.

Process cleanup

Repeated experiments can leave old backends, stale proxies, port conflicts, or hanging processes. The launcher cleans processes during restarts and shutdowns, which makes iterative development safer.

Google Colab and Drive

Colab is useful for CUDA inference but has temporary runtimes, possible restarts, no-Docker constraints, and files that can disappear. The launcher supports a workflow where benchmark results and logs can be saved to Google Drive.

Docker and no-Docker modes

Docker is convenient for local reproducibility, but it is not always available in Colab. The project supports both Docker and no-Docker modes while keeping scripts and .env as the common control surface.

Configuration through .env

BASE_MODEL_RUNNER_TYPE=vllm16GB
HF_TOKEN=hf_...
GAIA_TASK=inspect_evals/gaia_level1
GAIA_SPLIT=validation
FEATURE_SELF_CONSISTENCY=1
FEATURE_CONTEXT_COMPACTION=1
FEATURE_EXAMPLE=0

The file describes the experiment: backend runner, GAIA dataset access, task, split, and enabled techniques.

Backend-specific .env

BASE_MODEL_API_BASE_URL=http://127.0.0.1:18081/v1
BASE_MODEL_API_KEY=EMPTY
BASE_MODEL_NAME=qwen3.5-9b-q4

Backend-specific settings are separated from benchmark settings so the backend can be switched without mixing model, endpoint, and benchmark parameters.

Reproducibility

A saved .env describes which backend, model, benchmark task, split, techniques, and environment parameters were used. This is important when comparing runs and explaining differences.

Why this matters for small compute

The project is designed for limited compute: local CPU, Apple Silicon, Colab, one local GPU, quantized models, smaller models, limited context, limited memory, and slower inference. The launcher avoids binding the whole system to one ideal machine.

Place in the project

The launcher currently lives in the same repository as the proxy and GAIA/InspectAI runner. Later it can be extracted into gaia-experiment-launcher.

Audience

The launcher is useful for local GAIA runs, small-model benchmarks, backend comparisons, Colab runs, Apple Silicon development, reproducible evaluation runs, and teams with constrained compute.

Summary

GAIA Experiment Launcher handles the infrastructure side: it starts the benchmark pipeline, supports different inference backends, uses explicit configuration, saves logs, checks readiness, cleans processes, and makes experiments reproducible.
