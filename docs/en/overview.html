Short version

The project builds infrastructure for experimenting with language-model behavior inside a benchmark loop. The main practical target is GAIA through InspectAI, but the architecture is not tightly coupled to GAIA.

The project has two major parts:

1. Test-Time Scaling Proxy
2. GAIA Experiment Launcher

The proxy adds experimental techniques on top of an OpenAI-compatible model. The launcher makes the full pipeline reproducible across different inference backends and compute environments.

Main idea

The goal is to make LLM benchmark experiments faster, more modular, and reproducible. Instead of modifying the benchmark runner for every technique, the project introduces an intermediate layer:

Benchmark runner -> Proxy with techniques -> Base model backend

This layer can change prompts and requests, inspect responses, run extra model calls, aggregate answers, enable Best-of-N, save intermediate state, compact context, track tool calls, collect usage, combine techniques, and preserve run configuration.

Why not change the benchmark

The benchmark runner should stay clean. If every technique is embedded directly into benchmark code, the benchmark becomes harder to maintain, techniques become implementation-specific, comparisons become harder, and experiment code gets mixed with scoring and task execution.

The proxy owns experimental logic. The benchmark runs tasks and scores answers. The backend loads the model and serves responses.

Practical stack

GAIA Benchmark
        ↓
InspectAI GAIA runner
        ↓
Test-Time Scaling Proxy
        ↓
OpenAI-compatible model backend
        ↓
Local / Colab / Mac / GPU inference

For InspectAI, the proxy looks like a normal model. For the proxy, the base model looks like a normal OpenAI-compatible endpoint.

Why OpenAI-compatible API matters

The OpenAI-compatible API is a practical standard for local and remote inference backends. llama.cpp, vLLM, MLX-based serving, and other model servers can expose /v1/chat/completions.

If a benchmark runner can call an OpenAI-compatible endpoint, the proxy can be inserted between the benchmark and the model without deep integration work.

Research directions

The project studies test-time techniques that change model behavior through inference organization rather than training. Examples include Best-of-N, self-consistency, adaptive sampling, ranked voting, context compaction, structured notes, budget-aware reasoning, tool-result summarization, branch isolation, final-answer selection, and intermediate state tracking.

Test-time scaling

Test-time scaling tries to improve answer quality by spending more compute at inference time. The simplest version is to make several attempts and choose the best one. More advanced variants run independent reasoning branches, ask the model to verify its answer, use voting, estimate task difficulty, or allocate extra calls only to harder tasks.

Context optimization

In GAIA-like tasks, history can grow quickly: system prompt, task, reasoning, tool calls, tool results, observations, retries, and branch histories. For small-context models this can become a bottleneck.

The project supports techniques that compress long tool results, extract facts, save structured notes, remove irrelevant history, isolate branches, and manage accumulated messages.

Why small models matter

The project assumes realistic compute constraints: small open-source models, quantized models, local CPU, Apple Silicon, Google Colab, one local GPU, limited context, limited memory, and slower inference. In this setting, inference-time techniques can improve usefulness without training or heavy infrastructure.

Heterogeneous compute

llama.cpp       — CPU inference
llama.cpp CUDA  — Google Colab
vLLM            — local GPU machine
MLX             — Mac / Apple Silicon

The backend is selected through configuration. The benchmark runner does not depend on the backend, the proxy does not depend on a specific model, and the launcher knows how to start the chosen pipeline.

Project modularity

The project is split into two logical parts. The proxy / micro-framework handles experimental techniques. The runner / launcher handles reproducible experiment execution.

1. Proxy / micro-framework

This part provides an OpenAI-compatible proxy, hook points, task-local state, middleware chains, feature flags, technique modules, extra model calls, and answer aggregation.

2. Runner / launcher

This part starts the base model backend, proxy, and InspectAI / GAIA; performs readiness checks; saves logs; performs cleanup; handles backend-specific env; and supports multiple inference environments.

The project currently lives in one repository because the proxy, launcher, benchmark runner, and backend are tightly connected during active development. After stabilization, the infrastructure can be split into reusable components: tts-proxy-framework and gaia-experiment-launcher.

Project output

The output is not a single benchmark score. It is infrastructure that makes scores quick to produce and compare: a unified benchmark pipeline, a proxy layer for test-time techniques, hooks, task-local state, feature flags, Best-of-N support, context-saving techniques, launcher support for different backends, Colab support, Apple Silicon support, CPU/CUDA scenarios, reproducible env configuration, centralized logs, and a path to reusable components.

Typical experiment

1. Choose a backend
2. Choose a model
3. Configure GAIA task and split
4. Enable feature flags
5. Start the launcher
6. Launcher starts the backend
7. Launcher starts the proxy
8. Launcher starts InspectAI / GAIA
9. Proxy applies selected techniques
10. Benchmark receives final answers
11. Logs and results are saved
12. Configuration can be reproduced later

Audience

The project is intended for LLM behavior researchers, benchmark teams, test-time scaling developers, users of local open-source models, teams running GAIA without closed APIs, and people working under constrained compute.

Limitations

The focus is research and evaluation, not production serving. Extra model calls, experimental logic, detailed logs, and flexibility are expected. Latency is not the only optimization target.

Summary

The project creates practical infrastructure for adding, running, and comparing model-behavior techniques without rewriting the benchmark runner or locking the system to one inference backend.
