Short version

Test-Time Scaling Proxy is an OpenAI-compatible proxy over a base language model. It is designed for experiments with test-time scaling, Best-of-N, self-consistency, context-saving, and other lightweight techniques that can be inserted into a benchmark loop without changing the benchmark code.

InspectAI / GAIA -> Test-Time Scaling Proxy -> OpenAI-compatible model backend

The benchmark calls the proxy as a normal OpenAI-compatible model. The proxy can modify the request, call the base model, process the response, run additional model calls, aggregate results, and return one final response in the expected format.

Why a proxy

The goal is to make model-behavior experiments fast, reproducible, and extensible. Instead of embedding every new technique into the benchmark runner, a technique is implemented as a separate module and connected to task, model-call, and tool-call lifecycle hooks.

This is useful when many techniques need to be compared, techniques change often, some techniques require multiple internal calls, intermediate state must be preserved, the benchmark must remain unchanged, and the base model may run on different backends.

What the proxy does

The proxy accepts OpenAI-compatible requests and itself looks like a normal model to the benchmark runner. It can accept /v1/chat/completions, read messages and tools, change prompts or parameters, forward requests to the model backend, process JSON responses, run multiple internal calls, aggregate answers, select the best answer, track usage and state, and return one final response.

Supported technique classes

The proxy is best suited for techniques that naturally fit a hook-based model: Best-of-N, self-consistency, ranked voting, adaptive Best-of-N, budget tracking, context compaction, structured notes, ReSum-like methods, prompt modification, response analysis, tool-result summarization, usage tracking, and lightweight test-time scaling.

Heavy tree-search scaffolds, complex external planners, and production serving architectures are less natural fits, although parts of them can still be expressed through hooks.

Hook-based micro-framework

The proxy defines hooks for task lifecycle, model-call lifecycle, and tool-call lifecycle:

before_task_call / after_task_call
before_chat_message / after_chat_message
before_tool_call / after_tool_call

These hooks initialize technique state, modify requests, collect usage, log responses, save intermediate variants, compress tool results, manage context, and prepare data for later aggregation.

Technique interface

class Technique:
    feature_name = "FEATURE_MY_TECHNIQUE"

    def before_task_call(self, payload): ...
    def before_chat_message(self, payload): ...
    def after_chat_message(self, response): ...
    def after_task_call(self, response): ...
    def before_tool_call(self, response): ...
    def after_tool_call(self, payload): ...

A simple technique can be a single file and one class. It only needs to implement the hooks it uses.

Task-local state

Techniques can store counters, intermediate answers, usage, model-call counts, tool-call counts, original task payloads, branch payloads, voting results, compacted context, structured notes, complexity signals, and any data needed by later hooks.

This enables multi-step techniques such as Best-of-N, which needs to remember branches, collected answers, remaining attempts, and the selected final answer.

Composing techniques

Multiple techniques can be enabled at once. Active techniques form a linear middleware chain:

request/response -> Technique A hook -> Technique B hook -> Technique C hook

For example, one technique can track budget, another can compact context, a third can run Best-of-N, a fourth can collect structured notes, and a fifth can select the final answer.

Feature flags

FEATURE_SELF_CONSISTENCY=1
FEATURE_CONTEXT_COMPACTION=1
FEATURE_EXAMPLE=0

Feature flags make it easy to enable and disable techniques, save experiment configuration, reproduce runs, and compare technique sets.

Best-of-N example

Benchmark request
        ↓
TTS Proxy
        ↓
Branch 1 -> base model
Branch 2 -> base model
Branch 3 -> base model
        ↓
Aggregation / voting / selection
        ↓
Final response to benchmark

The benchmark receives one final answer and does not need to know that several internal attempts were made.

Context-saving example

In GAIA-like tasks, long tool results and accumulated history can become a problem for smaller models. The proxy can compress tool results, extract structured notes, remove irrelevant history, store compact task state, track context growth, and add a short state summary instead of full history.

Why this is not just a wrapper

A normal model wrapper usually only forwards requests. Test-Time Scaling Proxy adds a research-oriented lifecycle layer before and after tasks, model calls, tool calls, and tool results. This turns it into a micro-framework for benchmark experiments.

Responsibility boundary

The benchmark runner chooses the benchmark, loads tasks, runs scoring and tools, and evaluates results. The base model backend loads the model and performs inference. The proxy owns intervention points, techniques, state, extra calls, aggregation, context-saving, and OpenAI-compatible behavior toward the benchmark.

Place in the project

Today the micro-framework is part of a unified GAIA/InspectAI experiment project. Later it can be extracted into a reusable repository such as tts-proxy-framework.

Audience

The component is useful for test-time scaling researchers, benchmark infrastructure developers, teams comparing inference-time techniques, local-LLM users, small-model experimenters, and anyone who wants to separate benchmark code from experimental techniques.

Summary

Test-Time Scaling Proxy keeps the benchmark and model backend unchanged while techniques are added as modules, hooks provide lifecycle intervention points, task-local state enables multi-step methods, and feature flags make experiments reproducible.
