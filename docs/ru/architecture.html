Proxy micro framework

Кратко

Test-Time Scaling Proxy — это OpenAI-compatible proxy над базовой языковой моделью, предназначенный для экспериментов с test-time scaling, Best-of-N, self-consistency, context-saving и другими lightweight-техниками, которые можно встроить в benchmark loop без изменения кода самого benchmark’а.

Проект решает практическую задачу: benchmark runner, например InspectAI с GAIA, обычно вызывает модель как внешний endpoint. Если нужно проверить новую технику улучшения поведения модели на этапе инференса, приходится либо менять код benchmark’а, либо писать отдельную обвязку под каждую технику. Test-Time Scaling Proxy выносит эту логику в отдельный слой между benchmark’ом и базовой моделью.

Базовая схема:

InspectAI / GAIA → Test-Time Scaling Proxy → OpenAI-compatible model backend

Benchmark обращается к proxy как к обычной OpenAI-compatible модели. Proxy принимает запрос, при необходимости изменяет его, передаёт его в базовую модель, получает ответ, может обработать ответ, выполнить дополнительные model calls, агрегировать результаты и вернуть benchmark’у финальный response в ожидаемом формате.

Зачем нужен proxy

Главная цель proxy — сделать эксперименты с поведением модели быстрыми, воспроизводимыми и расширяемыми.

Вместо того чтобы каждый раз встраивать новую технику прямо в benchmark runner, техника оформляется как отдельный модуль. Такой модуль подключается к lifecycle benchmark-задачи, model call’ов и tool call’ов через заранее определённые hook points.

Это особенно полезно в условиях, когда:

  • нужно сравнивать много техник улучшения поведения модели;
  • техники часто меняются;
  • часть техник требует нескольких внутренних вызовов модели;
  • нужно сохранять промежуточное состояние между шагами;
  • benchmark должен оставаться неизменным;
  • базовая модель может запускаться разными backend’ами;
  • эксперимент не является production inference, а нужен именно для research / evaluation loop.

Что делает Test Time Scaling Proxy

Proxy принимает запросы в OpenAI-compatible формате и сам выглядит для benchmark runner’а как обычная модель.

На практике proxy может:

  • принять /v1/chat/completions request;
  • прочитать messages, tools, tool calls и параметры запроса;
  • изменить prompt или параметры перед отправкой в базовую модель;
  • передать запрос в OpenAI-compatible endpoint базовой модели;
  • получить JSON-ответ модели;
  • изменить ответ модели перед возвратом benchmark’у;
  • выполнить несколько внутренних вызовов модели;
  • агрегировать несколько ответов;
  • выбрать лучший ответ;
  • сохранить usage, счётчики, промежуточные результаты и внутренний state;
  • вернуть benchmark runner’у один финальный OpenAI-compatible response.

Для benchmark’а вся эта логика скрыта. Он продолжает считать, что работает с одной моделью.

Классы техник

Proxy предназначен не для любой возможной inference-архитектуры, а для техник, которые естественно ложатся на hook-based модель.

Хорошо подходят:

  • Best-of-N;
  • self-consistency;
  • ranked voting;
  • adaptive Best-of-N;
  • budget tracking;
  • context compaction;
  • structured notes;
  • ReSum-подобные техники;
  • техники с промежуточной записью reasoning state;
  • техники, которые изменяют prompt перед model call;
  • техники, которые анализируют response после model call;
  • техники, которые сжимают или преобразуют tool results;
  • техники, которые отслеживают usage, количество tool calls, длину контекста;
  • lightweight test-time scaling техники, не требующие полного переписывания execution loop.

Чуть менее естественно ложатся тяжёлые tree-search scaffold’ы, сложные внешние planners или production-level serving-архитектуры. Такие подходы тоже можно частично выражать через hooks, но этот proxy прежде всего создавался как удобная research-инфраструктура для benchmark-экспериментов.

Hook based micro framework

Внутри proxy реализован небольшой micro-framework с набором hook points. Они сгруппированы по lifecycle:

Task lifecycle

Эти hooks относятся к началу и завершению benchmark-задачи.

  • before_task_call
  • after_task_call

Они позволяют инициализировать state техники, сохранить исходный task payload, начать новую ветку, собрать финальный ответ, выбрать лучший результат или очистить состояние после завершения задачи.

Model call lifecycle

Эти hooks относятся к каждому вызову базовой модели.

  • before_chat_message
  • after_chat_message

Они позволяют модифицировать запрос перед отправкой в модель, добавлять инструкции, управлять историей сообщений, собирать usage, логировать ответы, сохранять промежуточные варианты и подготавливать данные для последующей агрегации.

Tool call lifecycle

Эти hooks относятся к вызовам инструментов и результатам инструментов.

  • before_tool_call
  • after_tool_call

Они позволяют отслеживать tool calls, модифицировать payload, сжимать tool results, сохранять наблюдения, управлять контекстом после использования инструментов и реализовывать техники, завязанные на tool-augmented reasoning.

Интерфейс и state

Новая техника добавляется как отдельная реализация общего interface.

Упрощённый вид:

class Technique:
    feature_name = "FEATURE_MY_TECHNIQUE"

    def before_task_call(self, payload): ...
    def before_chat_message(self, payload): ...
    def after_chat_message(self, response): ...
    def after_task_call(self, response): ...
    def before_tool_call(self, response): ...
    def after_tool_call(self, payload): ...

Техника не обязана содержать сложную инфраструктуру. В простом случае это один файл и один класс, который реализует только нужные hooks. Остальные hooks могут оставаться пустыми или не менять данные.

Task local state

Между hooks доступен task-local state. Это важная часть архитектуры.

Техника может хранить:

  • счётчики;
  • список промежуточных ответов;
  • usage;
  • количество model calls;
  • количество tool calls;
  • исходный payload задачи;
  • payload текущей ветки;
  • результаты голосования;
  • сжатый контекст;
  • structured notes;
  • внутренние признаки сложности задачи;
  • любые данные, нужные для последующего hook’а.

Task-local state позволяет реализовывать техники, которые не ограничиваются одним отдельным запросом к модели. Например, Best-of-N должен помнить, какие ветки уже были запущены, какие ответы получены, сколько попыток осталось и какой ответ выбран финальным.

Композиция и flags

Несколько техник могут быть включены одновременно.

Активные техники образуют linear middleware chain: каждый hook последовательно проходит через список включённых техник, а результат одного handler’а передаётся следующему.

Концептуально:

request/response → Technique A hook → Technique B hook → Technique C hook

Это позволяет собирать экспериментальные конфигурации из нескольких независимых техник.

Например:

  • одна техника считает budget;
  • вторая сжимает контекст;
  • третья запускает Best-of-N;
  • четвёртая собирает structured notes;
  • пятая выбирает финальный ответ.

Такая композиция не требует переписывать benchmark runner и не требует объединять все техники в один монолитный модуль.

Feature flags

Техники включаются через feature flags в .env.

Пример:

FEATURE_SELF_CONSISTENCY=1
FEATURE_CONTEXT_COMPACTION=1
FEATURE_EXAMPLE=0

Это даёт несколько преимуществ:

  • можно быстро включать и отключать техники;
  • можно сохранять конфигурацию эксперимента;
  • можно воспроизводить запуск позже;
  • можно сравнивать несколько наборов техник;
  • можно запускать один и тот же benchmark с разными experimental settings.

Примеры техник

Best-of-N — хороший пример техники, ради которой полезен proxy.

Снаружи benchmark делает обычный вызов модели. Внутри proxy может выполнить несколько независимых branch’ей:

Benchmark request
        ↓
TTS Proxy
        ↓
Branch 1 → base model
Branch 2 → base model
Branch 3 → base model
        ↓
Aggregation / voting / selection
        ↓
Final response to benchmark

Benchmark получает один финальный ответ и не знает, что под капотом было несколько внутренних попыток.

Для такой техники нужны:

  • сохранение исходного task payload;
  • запуск нескольких веток;
  • изоляция истории веток;
  • сбор ответов;
  • выбор финального ответа;
  • возврат одного response в OpenAI-compatible формате.

Context saving техники

В GAIA-подобных задачах модель может использовать инструменты, получать длинные tool results и постепенно накапливать контекст. Для маленьких моделей или моделей с ограниченным контекстом это становится проблемой.

Proxy позволяет реализовывать context-saving техники:

  • сжимать длинные tool results;
  • выделять structured notes;
  • удалять лишние фрагменты истории;
  • сохранять компактное состояние задачи;
  • отслеживать рост контекста;
  • добавлять в prompt краткое состояние вместо полной истории.

Это особенно важно в условиях ограниченного compute, когда используются небольшие локальные модели, quantized-модели или модели с небольшим context window.

Границы proxy

Обычный wrapper вокруг модели чаще всего только пересылает запросы. Test-Time Scaling Proxy добавляет research-oriented lifecycle layer.

Он не просто передаёт request в backend, а создаёт точку вмешательства в benchmark loop:

  • до task;
  • до model call;
  • после model call;
  • до tool call;
  • после tool result;
  • после завершения task.

Это превращает proxy в micro-framework для экспериментов, а не просто в HTTP-прокси.

Где находится граница ответственности

Test-Time Scaling Proxy не заменяет benchmark runner и не заменяет model backend.

Benchmark runner отвечает за:

  • выбор benchmark’а;
  • загрузку задач;
  • scoring;
  • execution loop;
  • tools;
  • оценку результата.

Base model backend отвечает за:

  • загрузку модели;
  • inference;
  • OpenAI-compatible endpoint;
  • работу конкретного backend’а: llama.cpp, vLLM, MLX и т.д.

Test-Time Scaling Proxy отвечает за:

  • экспериментальные intervention points;
  • подключение техник;
  • task-local state;
  • дополнительные model calls;
  • агрегацию;
  • context-saving;
  • сохранение OpenAI-compatible interface для benchmark’а.

Место и аудитория

Сейчас micro-framework является частью единого проекта для запуска GAIA/InspectAI экспериментов. В дальнейшем он может быть выделен в отдельный репозиторий как самостоятельный reusable-компонент.

Потенциальное направление выделения:

tts-proxy-framework

Такой репозиторий мог бы использоваться не только для GAIA, а для любых benchmark’ов или evaluation loops, которые умеют обращаться к OpenAI-compatible model endpoint.

Для кого этот компонент

Компонент полезен для:

  • исследователей test-time scaling;
  • разработчиков benchmark-инфраструктуры;
  • команд, которые сравнивают inference-time техники;
  • тех, кто работает с локальными LLM;
  • тех, кто хочет экспериментировать с small models;
  • тех, кто хочет отделить benchmark code от experimental techniques;
  • тех, кто хочет быстро прототипировать новые scaffold’ы поверх OpenAI-compatible моделей.

Итог

Test-Time Scaling Proxy делает benchmark-эксперименты проще:

  • benchmark остаётся неизменным;
  • модель остаётся обычным OpenAI-compatible backend’ом;
  • техники добавляются как отдельные модули;
  • hooks дают точки вмешательства в lifecycle задачи;
  • task-local state позволяет реализовывать multi-step техники;
  • feature flags делают эксперименты воспроизводимыми;
  • разные техники можно комбинировать в одном запуске.

Главная идея: отделить исследовательские техники от benchmark runner’а и model backend’а, превратив их в подключаемый слой между ними.

Runner infrastructure

Кратко

GAIA Experiment Launcher — это инфраструктурная часть проекта, которая запускает полный экспериментальный контур:

base model backend → Test-Time Scaling Proxy → InspectAI / GAIA

Launcher нужен для того, чтобы один и тот же benchmark можно было воспроизводимо запускать на разных inference backend’ах и в разных вычислительных средах: CPU, CUDA, Google Colab, Mac / Apple Silicon.

Главная задача launcher’а — убрать ручную сборку окружения и сделать запуск экспериментов повторяемым.

Проблема и схема

Эксперименты с локальными LLM часто зависят от среды запуска.

Одна модель может запускаться через llama.cpp на CPU, другая через llama.cpp CUDA в Colab, третья через MLX на Apple Silicon, четвёртая через vLLM на локальной GPU-машине. При этом benchmark runner и proxy должны получать одинаковый OpenAI-compatible endpoint.

Без launcher’а каждый запуск превращается в набор ручных действий:

  • поднять model backend;
  • проверить, что модель загрузилась;
  • поднять proxy;
  • проверить, что proxy доступен;
  • запустить InspectAI / GAIA;
  • правильно передать endpoint;
  • не забыть API key;
  • сохранить логи;
  • очистить процессы после падения;
  • повторить это всё на другой машине.

Launcher автоматизирует этот процесс.

Общая схема запуска

Pipeline состоит из трёх основных частей:

1. Base model backend
2. Test-Time Scaling Proxy
3. InspectAI / GAIA benchmark runner

Base model backend поднимает модель и предоставляет OpenAI-compatible API.

Test-Time Scaling Proxy подключается к backend’у и сам предоставляет OpenAI-compatible API для benchmark runner’а.

InspectAI / GAIA обращается к proxy как к модели и выполняет benchmark tasks.

Launcher и backend

В проекте важно не просто один раз запустить benchmark, а многократно запускать разные конфигурации:

  • разные модели;
  • разные backend’ы;
  • разные техники;
  • разные feature flags;
  • разные уровни GAIA;
  • разные split’ы;
  • разные среды запуска;
  • Docker / no-Docker режимы;
  • локальные машины и Colab.

Launcher превращает запуск в воспроизводимый процесс, управляемый конфигурацией.

Поддержанные варианты inference

В текущей инфраструктуре поддерживаются четыре основных варианта inference:

llama.cpp       — CPU inference
llama.cpp CUDA  — Google Colab
vLLM            — локальная GPU-машина
MLX             — Mac / Apple Silicon

Эти варианты закрывают несколько практических сценариев.

llama.cpp CPU inference

Используется для запуска моделей на CPU. Это полезно, когда нет доступной GPU или когда нужно проверить работоспособность pipeline на простой машине.

CPU inference медленный, но удобен как baseline и fallback.

llama.cpp CUDA Google Colab

Используется для запуска на CUDA в Google Colab. Это важный сценарий, потому что Colab позволяет получить GPU без настройки собственной машины.

Для Colab особенно важен no-Docker режим, так как Docker не всегда доступен или удобен в notebook-среде.

vLLM локальная GPU машина

vLLM используется как вариант запуска на локальной GPU-машине. Он полезен как backend для OpenAI-compatible serving, хотя в конкретных экспериментах мог показывать себя хуже или быть менее удобным, чем другие варианты.

Важно, что launcher отделяет сам benchmark pipeline от конкретного backend’а: даже если один backend подходит плохо, его можно заменить без изменения логики benchmark’а и proxy.

MLX Mac Apple Silicon

MLX используется для запуска на Mac / Apple Silicon. Это важно для локальной разработки и экспериментов на Apple hardware.

Такой режим позволяет использовать Mac как полноценную среду для проверки pipeline, не требуя CUDA.

Что делает launcher

Launcher последовательно запускает части pipeline:

base model backend → TTS Proxy → InspectAI / GAIA

Затем он контролирует готовность компонентов, сохраняет логи и помогает воспроизводить запуск.

Основные функции:

  • последовательно запускает части pipeline;
  • проверяет готовность endpoint’ов;
  • чистит процессы при перезапусках;
  • сохраняет stdout/stderr-логи всех частей в одном месте;
  • в Colab может сохранять результаты и логи на Google Drive;
  • использует .env для управления конфигурацией;
  • позволяет переключать backend без переписывания scripts;
  • отделяет общие параметры benchmark’а от backend-specific параметров.

Готовность endpoint’ов

Компоненты pipeline зависят друг от друга: InspectAI / GAIA не должен стартовать раньше proxy, proxy не должен начинать работу без доступного base model backend, а base model backend должен сначала загрузить модель и открыть endpoint.

Поэтому launcher запускает pipeline последовательно:

1. Сначала base model backend
2. Потом Test-Time Scaling Proxy
3. Потом InspectAI / GAIA benchmark

После запуска каждого компонента launcher выполняет readiness checks. Сам факт запуска процесса ещё не означает, что компонент готов принимать запросы: model backend может стартовать быстро, но продолжать загружать модель в память; proxy может быть запущен, но ещё не отвечать на /health или OpenAI-compatible endpoint.

Launcher проверяет готовность endpoint’ов перед переходом к следующему этапу. Это уменьшает количество ручных ошибок и особенно важно для тяжёлых моделей и удалённых/нестабильных сред, например Google Colab.

Логи и очистка процессов

Для benchmark-экспериментов важна отладка. Если запуск падает, нужно понимать, где именно произошла ошибка:

  • backend не загрузил модель;
  • proxy не смог подключиться к backend’у;
  • benchmark runner получил ошибку;
  • endpoint не поднялся;
  • закончилась память;
  • сломалась конфигурация;
  • техника внутри proxy вернула некорректный response.

Поэтому launcher сохраняет stdout/stderr-логи всех частей в одном месте.

Это позволяет восстановить ход запуска и понять, какая часть pipeline сломалась.

Очистка процессов

При экспериментах часто происходят падения, зависания или повторные запуски. Если не чистить процессы, можно получить конфликт портов, старый backend, старый proxy или несколько конкурирующих процессов.

Launcher чистит процессы при перезапусках и завершении работы.

Это особенно полезно при многократной итерации:

  • поменяли .env;
  • включили новую feature;
  • перезапустили benchmark;
  • получили новые логи;
  • повторили запуск с другой моделью.

Colab и Docker

Google Colab важен как доступная среда для CUDA inference. Но Colab имеет особенности:

  • окружение временное;
  • процессы могут падать;
  • runtime может быть перезапущен;
  • файлы могут потеряться;
  • Docker может быть недоступен или неудобен;
  • нужно отдельно сохранять результаты.

Поэтому launcher поддерживает сценарий, где в Colab можно сохранять результаты benchmark’а и логи на Google Drive.

Это делает Colab не просто одноразовой средой, а пригодным compute backend’ом для серии экспериментов.

Docker и no Docker режимы

Проект учитывает, что разные среды требуют разных способов запуска.

Docker удобен для локальной воспроизводимости, но не всегда доступен в Colab. Поэтому launcher поддерживает no-Docker сценарий.

Разделение важно:

  • локально можно запускать через Docker;
  • в Colab можно запускать без Docker;
  • scripts и .env остаются общей точкой управления;
  • benchmark pipeline сохраняет одинаковую структуру.

Env конфигурация

Один из принципов проекта — конфигурация должна быть явной и сохраняемой.

Минимальный пример общей конфигурации:

# 1. Где запускаем base model backend
BASE_MODEL_RUNNER_TYPE=vllm16GB

# 2. Доступ к GAIA dataset
HF_TOKEN=hf_...

# 3. Параметры benchmark'а
GAIA_TASK=inspect_evals/gaia_level1
GAIA_SPLIT=validation

# 4. Какие техники включены
FEATURE_SELF_CONSISTENCY=1
FEATURE_CONTEXT_COMPACTION=1
FEATURE_EXAMPLE=0

Этот файл управляет:

  • выбором backend runner’а;
  • доступом к GAIA dataset;
  • benchmark task;
  • split’ом;
  • включёнными экспериментальными техниками.

Backend specific env

Общие параметры benchmark’а отделяются от backend-specific настроек.

Пример backend-specific конфигурации:

BASE_MODEL_API_BASE_URL=http://127.0.0.1:18081/v1
BASE_MODEL_API_KEY=EMPTY
BASE_MODEL_NAME=qwen3.5-9b-q4

Это позволяет переключать backend, не смешивая параметры модели, endpoint’а и benchmark’а в одном месте.

Общий .env отвечает за эксперимент. Backend-specific .env отвечает за конкретный способ запуска базовой модели.

Воспроизводимость

Сохранённый .env фактически описывает запуск.

По нему можно понять:

  • какой backend использовался;
  • какая модель была подключена;
  • какой benchmark task запускался;
  • какой split использовался;
  • какие техники были включены;
  • какие параметры окружения были важны.

Это важно для research workflow, где нужно сравнивать результаты и понимать, чем один запуск отличался от другого.

Small compute

Проект создавался в условиях ограниченного compute. Это влияет на архитектуру.

Когда нет большого кластера GPU, приходится использовать разнородные ресурсы:

  • локальный CPU;
  • Mac / Apple Silicon;
  • Google Colab;
  • локальная GPU;
  • quantized-модели;
  • маленькие модели;
  • разные backend’ы.

Launcher позволяет не привязывать весь проект к одному идеальному inference setup. Вместо этого pipeline можно переносить между доступными средами.

Место и аудитория

Сейчас launcher является частью единого проекта, который включает и proxy, и GAIA/InspectAI запуск.

В дальнейшем launcher может быть выделен в отдельный репозиторий:

gaia-experiment-launcher

Такой репозиторий мог бы использоваться отдельно от конкретного набора test-time техник и служить инфраструктурой для запуска GAIA/InspectAI на разных compute backend’ах.

Для кого этот компонент

Launcher полезен для:

  • локального запуска GAIA;
  • запуска benchmark’ов на маленьких моделях;
  • сравнения backend’ов;
  • запуска в Google Colab;
  • запуска на Mac / Apple Silicon;
  • воспроизводимых evaluation runs;
  • research-команд с ограниченным compute;
  • быстрого переключения между моделями и inference backend’ами.

Итог

GAIA Experiment Launcher решает инфраструктурную часть проекта:

  • запускает полный benchmark pipeline;
  • поддерживает разные inference backend’ы;
  • работает с разнородным compute;
  • управляется через .env;
  • сохраняет логи;
  • проверяет готовность endpoint’ов;
  • очищает процессы;
  • помогает воспроизводить эксперименты.

Главная идея: запуск benchmark’а должен быть таким же воспроизводимым и переключаемым, как конфигурация эксперимента.
