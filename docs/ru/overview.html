About проекта

Benchmark становится стабильной лабораторией: техники можно менять и сравнивать, не переписывая runner и не привязываясь к одному backend.

Кратко

Проект создаёт инфраструктуру для экспериментов с поведением языковых моделей в benchmark loop. Основной практический сценарий — GAIA Benchmark через InspectAI, но архитектура не привязана жёстко только к GAIA.

Проект состоит из двух больших частей:

1. Test-Time Scaling Proxy
2. GAIA Experiment Launcher

Первая часть отвечает за подключение experimental techniques поверх OpenAI-compatible модели.

Вторая часть отвечает за воспроизводимый запуск полного pipeline на разных inference backend’ах и в разных вычислительных средах.

Главная идея

Цель проекта — сделать benchmark-эксперименты с LLM более быстрыми, модульными и воспроизводимыми.

Вместо того чтобы каждый раз менять benchmark runner или писать отдельный pipeline под каждую технику, проект вводит промежуточный слой:

Benchmark runner → Proxy with techniques → Base model backend

Этот слой позволяет экспериментировать с поведением модели на этапе выполнения benchmark’а:

  • менять prompt;
  • менять request;
  • анализировать response;
  • запускать дополнительные model calls;
  • агрегировать ответы;
  • включать Best-of-N;
  • сохранять промежуточное состояние;
  • сжимать контекст;
  • отслеживать tool calls;
  • собирать usage;
  • комбинировать несколько техник;
  • сохранять конфигурацию запуска.

Почему не менять сам benchmark

Benchmark runner должен оставаться максимально чистым.

Если каждая техника будет встраиваться прямо в benchmark code, появятся проблемы:

  • benchmark станет сложнее поддерживать;
  • техники будут зависеть от конкретной реализации benchmark’а;
  • будет трудно сравнивать техники между собой;
  • будет трудно отключать одну технику и включать другую;
  • будет трудно переносить подход на другой benchmark;
  • будет трудно воспроизводить результаты;
  • код экспериментов смешается с кодом scoring и task execution.

Поэтому проект выносит экспериментальную логику в proxy layer.

Benchmark продолжает делать то, что должен делать benchmark: запускать задачи и оценивать ответы.

Proxy делает то, что нужно для экспериментов: вмешивается в model/tool/task lifecycle и реализует техники.

Backend делает то, что должен делать backend: запускает модель и отдаёт ответы.

Практическая связка

Текущая практическая связка проекта:

GAIA Benchmark
        ↓
InspectAI GAIA runner
        ↓
Test-Time Scaling Proxy
        ↓
OpenAI-compatible model backend
        ↓
Local / Colab / Mac / GPU inference

Для InspectAI proxy выглядит как обычная модель. Для proxy базовая модель выглядит как обычный OpenAI-compatible endpoint.

Таким образом, обе стороны остаются простыми:

  • benchmark не знает о техниках;
  • base model backend не знает о benchmark’е;
  • proxy связывает их и добавляет experimental logic.

Что именно исследуется

Проект предназначен для исследования test-time техник, которые меняют поведение модели не через обучение, а через организацию инференса.

Примеры направлений:

  • Best-of-N;
  • self-consistency;
  • adaptive sampling;
  • ranked voting;
  • context compaction;
  • structured notes;
  • budget-aware reasoning;
  • tool-result summarization;
  • branch isolation;
  • final answer selection;
  • intermediate state tracking.

Общая идея: не менять веса модели, а улучшать её работу за счёт того, как она вызывается, как хранится контекст, как обрабатываются промежуточные результаты и как выбирается финальный ответ.

Test time scaling

Test-time scaling — это класс подходов, где качество ответа пытаются повысить за счёт дополнительных вычислений во время инференса.

Простейший пример — сделать несколько попыток и выбрать лучшую.

Более сложные варианты:

  • запустить несколько независимых веток рассуждения;
  • заставить модель проверить собственный ответ;
  • использовать голосование;
  • оценить сложность задачи и адаптивно выбрать compute budget;
  • сохранить промежуточные выводы;
  • использовать дополнительные model calls только для сложных задач.

Проект не ограничивается строгим определением test-time scaling. В нём также важны context-saving техники, потому что в реальных условиях compute ограничен, а модели могут быть небольшими.

Context optimization

Context optimization — важная часть проекта.

В GAIA-подобных задачах история может быстро расти:

  • system prompt;
  • user task;
  • assistant reasoning;
  • tool calls;
  • tool results;
  • промежуточные наблюдения;
  • повторные попытки;
  • branch histories.

Для моделей с небольшим context window это становится bottleneck’ом. Даже если модель потенциально может решить задачу, она может потерять важную информацию, переполнить контекст или начать хуже работать на длинной истории.

Поэтому проект поддерживает техники, которые:

  • сжимают длинные tool results;
  • выделяют факты;
  • сохраняют structured notes;
  • очищают лишнюю историю;
  • изолируют ветки;
  • уменьшают контекст между попытками;
  • управляют накоплением сообщений;
  • позволяют маленьким моделям эффективнее работать с benchmark tasks.

Почему маленькие модели важны

Проект учитывает практическую ситуацию: не всегда есть доступ к большим закрытым моделям или большому GPU-кластеру.

Часто доступны:

  • небольшие open-source модели;
  • quantized-модели;
  • локальный CPU;
  • Mac / Apple Silicon;
  • Google Colab;
  • одна локальная GPU;
  • ограниченный контекст;
  • ограниченная память;
  • медленный inference.

В таких условиях особенно важны техники, которые повышают полезность модели без обучения и без тяжёлой инфраструктуры.

Разнородный compute как часть задачи

Проект не предполагает одну фиксированную машину.

Эксперименты могут запускаться на разных средах:

llama.cpp       — CPU inference
llama.cpp CUDA  — Google Colab
vLLM            — локальная GPU-машина
MLX             — Mac / Apple Silicon

Это влияет на весь дизайн:

  • backend выбирается конфигурацией;
  • benchmark runner не зависит от backend’а;
  • proxy не зависит от конкретной модели;
  • launcher знает, как поднять нужный pipeline;
  • результаты и логи сохраняются отдельно;
  • запуск можно воспроизвести.

Модульность проекта

Проект логически делится на две части: proxy / micro-framework отвечает за experimental techniques, а runner / launcher — за воспроизводимый запуск эксперимента.

Proxy micro framework

Эта часть даёт OpenAI-compatible proxy, hook points, task-local state, middleware chain, feature flags, отдельные модули техник, дополнительные model calls и агрегацию ответов.

Runner launcher

Эта часть запускает base model backend, proxy и InspectAI / GAIA, делает readiness checks, сохраняет logs, выполняет cleanup, учитывает backend-specific env и поддерживает разные inference-среды.

Сейчас проект остаётся единым репозиторием, потому что proxy, launcher, benchmark runner и model backend тесно связаны в практическом запуске. Это удобно на этапе активной разработки, когда одновременно меняются hooks, набор техник, scripts, Colab workflow, структура логов и benchmark configuration.

После стабилизации инфраструктуру можно разделить на два reusable/open-source компонента: tts-proxy-framework для hook-based proxy и gaia-experiment-launcher для запуска GAIA/InspectAI на разнородном compute.

Вместе эти части дают полный research loop.

Что считается результатом проекта

Результат проекта — не один конкретный score на benchmark’е, а инфраструктура, которая позволяет быстро получать и сравнивать такие scores.

Вклад проекта:

  • единый benchmark pipeline;
  • proxy layer для test-time техник;
  • hook-based micro-framework;
  • task-local state;
  • feature flags;
  • поддержка Best-of-N и похожих техник;
  • context-saving возможности;
  • launcher для разных backend’ов;
  • Colab support;
  • Mac / Apple Silicon support;
  • CPU / CUDA scenarios;
  • воспроизводимая .env-конфигурация;
  • centralized logs;
  • возможность будущего разделения на reusable-компоненты.

Как выглядит типовой эксперимент

Типовой workflow:

1. Выбрать backend
2. Выбрать модель
3. Настроить GAIA task и split
4. Включить нужные feature flags
5. Запустить launcher
6. Launcher поднимает backend
7. Launcher поднимает proxy
8. Launcher запускает InspectAI / GAIA
9. Proxy применяет выбранные техники
10. Benchmark получает финальные ответы
11. Logs и результаты сохраняются
12. Конфигурация может быть воспроизведена позже

Пример конфигурации

# 1. Где запускаем base model backend
BASE_MODEL_RUNNER_TYPE=vllm16GB

# 2. Доступ к GAIA dataset
HF_TOKEN=hf_...

# 3. Параметры benchmark'а
GAIA_TASK=inspect_evals/gaia_level1
GAIA_SPLIT=validation

# 4. Какие техники включены
FEATURE_SELF_CONSISTENCY=1
FEATURE_CONTEXT_COMPACTION=1
FEATURE_EXAMPLE=0

Backend-specific часть:

BASE_MODEL_API_BASE_URL=http://127.0.0.1:18081/v1
BASE_MODEL_API_KEY=EMPTY
BASE_MODEL_NAME=qwen3.5-9b-q4

Такой подход делает запуск понятным: один файл описывает эксперимент, другой описывает конкретный backend.

Для кого проект

Проект предназначен для:

  • исследователей LLM behavior;
  • команд, работающих с benchmark’ами;
  • разработчиков test-time scaling техник;
  • пользователей локальных open-source моделей;
  • тех, кто хочет запускать GAIA без закрытых API;
  • тех, кто работает с ограниченным compute;
  • тех, кто хочет сравнивать inference-time techniques;
  • тех, кто хочет отделить benchmark code от experimental code.

Ограничения

Проект ориентирован на исследовательские benchmark-запуски, а не на production serving.

Это значит:

  • главный фокус — удобство исследования;
  • допустимы дополнительные model calls;
  • допустима экспериментальная логика;
  • важна воспроизводимость;
  • важны логи;
  • важна гибкость;
  • latency не является единственным главным критерием.

Также проект не обещает поддержку любых возможных scaffold’ов. Он лучше всего подходит для техник, которые можно выразить через lifecycle hooks и middleware chain.

Итог

Проект создаёт практическую инфраструктуру для экспериментов с LLM в benchmark loop.

Он объединяет:

  • OpenAI-compatible proxy;
  • hook-based micro-framework;
  • feature-based подключение техник;
  • task-local state;
  • context-saving и test-time scaling подходы;
  • launcher для GAIA/InspectAI;
  • поддержку разных inference backend’ов;
  • воспроизводимую конфигурацию.

Главная идея: сделать так, чтобы новые техники поведения модели можно было добавлять, запускать и сравнивать быстро — без переписывания benchmark runner’а и без привязки к одному inference backend’у.
